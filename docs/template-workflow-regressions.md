# Template workflow checks

No automated suite or trial recorder is bundled. Use isolated copies and [manual trial records](guide/05-skill-evaluations.md); retain prompts, outputs, edit diffs and actual checks. These scenarios are planned, not claimed installed-host results.

| Scenario | Expected behavior |
| --- | --- |
| New short brief without advance | Understand only, product-design/1.3 with Phase/Level, decision brief only; no SRS or Test Plan just to fill template fields |
| Say next after discovery | Shape at design-documents, no confirmation/level interview; compare current/no-build and credible options, brief plus evaluation Test Plan with C cases; no SRS |
| Say full without advance in Shape | Remain in Shape; no premature SRS or claim that the cap grants approval |
| Advance to Full Specify | SRS build-spec/2.0 with seven sections and Requirements matrix; extend the same plan with verification C cases; preserve prior evaluation criteria/results |
| Missing project manager, schedule or target | Explicit unknown or useful decision trigger, not invented metadata or another preference interview |
| Planned check | Actual result: not run; matrix status planned; no claim that acceptance, demand, usability or human approval was demonstrated |
| Supplied research results | Attribute source/date/version/method/limitations, compare with predeclared criteria, preserve contradictions and update the brief's recommendation/history; do not present research as deterministic conformance checks |
| Rule changes after results | Update owning BR/R/A definitions first, affected C procedures and matrix status, copy and readiness; an old pass cannot verify changed behavior |
| Legacy package review or cosmetic revision | Preserve format and human edits, no automatic migration; standalone review is read-only |
| Authorized legacy migration | Preserve IDs/history/evidence, move old facts into SRS sections and procedures/results into plan, replace duplicate definitions with links; requirements matrix is embedded, not another canonical document |
| Request architecture/API/incident templates | Explain scope; do not add them to every run or imply this product plugin now authors engineering architecture |

Check both directions of traceability semantically. A correct ID in the wrong context is still inadequate. Judge Design coherence, Evidence confidence and Delivery readiness independently, and record blockers with owners or unknown. Do not infer investment or launch approval from a generated document.
