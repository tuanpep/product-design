# ERD Draw.io

Read [principle-one-source-of-truth](../principle-one-source-of-truth/SKILL.md), [principle-settle-the-logical-model](../principle-settle-the-logical-model/SKILL.md), [principle-keep-the-schemas-apart](../principle-keep-the-schemas-apart/SKILL.md), [principle-design-every-state](../principle-design-every-state/SKILL.md), [principle-protect-before-you-enable](../principle-protect-before-you-enable/SKILL.md), [principle-spend-less-of-the-world](../principle-spend-less-of-the-world/SKILL.md), and [principle-decide-the-reversible](../principle-decide-the-reversible/SKILL.md). The diagram draws the data design. It does not invent identifiers, cardinality, or columns. The logical page is the logical model. The physical page is the proposed internal schema. Neither page is the service contract. A physical schema is a proposal for builders, not a migration.

1. Name the question the diagram answers, for example: can a cover request exist without a shift? Read the domain model for attributes and cardinality, and the logical additions written by `design-data` for identifiers and normalization. If those additions are missing, run `design-data` first. Also read States and lifecycle and Integrations and data so external references and status values match.
2. Write uncompressed XML in `docs/product-design/<slug>/`, following [the Draw.io file skeleton](../drawio/references/drawio-file.md) and [the ERD components](references/erd-components.md). One cluster of related entities keeps `erd.drawio`, with logical and physical as its two pages. A second cluster that shares no relationship with the first is `1-<cluster>/erd.drawio`, numbered in parent/child index order, as [one file per close flow](../drawio/references/drawio-file.md#one-file-per-close-flow). Put it in the step folder when that step owns the entities.
3. **Logical page.** One entity per domain-model entity, named with its glossary term. List the attributes, required or optional, and personal or sensitive marks from the domain model. List the primary key, alternate key, and foreign keys from the logical additions. Do not add types. An attribute or entity the domain model lacks goes back to `model-domain` first. A key the logical additions lack goes back to `design-data` first.
4. Draw each relationship with crow's-foot ends that match the domain model's cardinality: exactly one, zero or one, one or many, zero or many. Label it with the verb the domain model uses. When an entity relates to another twice, draw both relationships and name each role.
5. Draw associative entities, and only those normalization exceptions, that the logical additions already record. Do not resolve a many-to-many on the diagram alone.
6. An entity whose system of record is another system is an external reference: draw it with the external style, and link it with the integration ID (I1) instead of a foreign key the product cannot enforce.
7. **Physical page.** Draw it only when `design-data` wrote a physical proposal. Copy its tables, types, nullability, keys, and indexes. Mark each table existing, changed, or new as that proposal does. Skip the page when the proposal says the slice stores nothing.
8. On the physical page, show the columns, types, nullability, defaults, keys, on-delete behavior, and indexes the proposal already lists. A status column uses the states in States and lifecycle; reference that section instead of copying the list into the diagram. A column or index the proposal lacks goes back to `design-data` first.
9. Mark personal or sensitive columns as the proposal does. Do not add audit, history, or soft-delete columns on the diagram.
10. Keep each **proposed** label and owner from the proposal. A blocking data question stays in Assumptions and open questions in `build-spec.md`, not only in a shape note.
11. Check the file: unique cell ids on each page, every row's parent is its table and every cell's parent is its row, every row has the same columns, every relationship runs between two rows, no two relationships share a segment ([Edges do not overlap](../drawio/references/drawio-file.md#edges-do-not-overlap)), and every entity in the domain model appears on the logical page. Open it in Draw.io or diagrams.net before claiming that it renders. If you could not open it, say so.

Link the file under Domain model in `build-spec.md` and under Information model in `technical-design.md` when that file exists, with its question. The domain model stays the source for attributes and relationships. The logical additions stay the source for identifiers, normalization, and the physical proposal. The diagram references them. The service contract stays in `technical-design.md`. Do not write SQL, migrations, or ORM code. The diagram is **proposed**. It is not evidence that the schema performs, migrates safely, or meets a retention policy.

**Reply:** the file path, the question, the entities and relationships, any external references, whether a physical page was drawn and whose conventions it follows, the proposed physical choices with owners, the blocking data questions, and what the diagram does not test.
