# ERD Draw.io

Apply [the shared execution contract](../design-product/references/specialist-execution.md). Principle links below are selective candidates, not mandatory preloads; read a leaf before citing it.

Use [principle triggers](../design-product/references/principles.md) selectively: single ownership, logical clarity, schema separation, lifecycle, protection, retained-data cost and reversible defaults. The diagram draws the data design. It does not invent identifiers, cardinality, or columns. The logical page uses PascalCase identifiers derived from the glossary; the physical page uses schema identifiers (`snake_case` when conventional). Neither uses spaced prose labels or represents the service contract. A physical schema is a proposal, not a migration. Naming rules and sources are in [erd-research.md](references/erd-research.md).

1. Name the question the diagram answers, for example: can a cover request exist without a shift? Read the domain model for attributes and cardinality, and the logical additions written by `design-data` for identifiers and normalization. If those additions are missing, run `design-data` first. Also read States and lifecycle and Integrations and data so external references and status values match.
2. **Always split logical and physical ERDs into separate files.** Write uncompressed XML in `docs/product-design/<slug>/`, following [the Draw.io file skeleton](../drawio/references/drawio-file.md) and [the ERD components](references/erd-components.md). Match the specimens [example-logical.drawio](references/example-logical.drawio), [example-physical.drawio](references/example-physical.drawio), and [example-erd.md](references/example-erd.md). One cluster of related entities uses `erd-logical.drawio` and, when a physical proposal exists, `erd-physical.drawio`. Each file has exactly one page. Do not create a combined `erd.drawio`. Multiple unrelated clusters use `1-<cluster>/erd-logical.drawio` and `1-<cluster>/erd-physical.drawio`, numbered in parent/child index order, as [one file per close flow](../drawio/references/drawio-file.md#one-file-per-close-flow). Put the files in the step folder when that step owns the entities. When revising a combined ERD, preserve each view in its separate file, update all links, and remove the old combined file; do not retain duplicate outputs.
3. **Logical file (`erd-logical.drawio`).** One entity per domain-model entity in this cluster. Name entities, attributes, and keys with the [Naming](references/erd-components.md#naming) rules. Do not add types or physical column names. An attribute or entity the domain model lacks goes back to `model-domain` first. A key the logical additions lack goes back to `design-data` first.
4. Draw each relationship with the crow's-foot ends in [Relationships](references/erd-components.md#relationships). Cardinality comes from the domain model. Place tables and route lines with [Layout](references/erd-components.md#layout). When an entity relates to another twice, draw both relationships and name each role.
5. Draw associative entities, and only those normalization exceptions, that the logical additions already record. Do not resolve a many-to-many on the diagram alone.
6. An entity whose system of record is another system is an external reference: draw it with the external style, in the rightmost column, and link it with the integration ID (I1) instead of a foreign key the product cannot enforce.
7. **Physical file (`erd-physical.drawio`).** Draw it only when `design-data` wrote a physical proposal. Check [the physical database design standard](../design-data/references/database-standard.md#physical-erd-acceptance). Use English for authored captions, legends, notes, and new identifiers; preserve existing identifiers and externally governed codes exactly. Copy its tables, types, nullability, keys, and indexes using the proposal's identifiers, not PascalCase or glossary phrases. Name the target engine/version or retain the engine unresolved qualification. Mark each table existing, changed, or new as that proposal does. Skip the file when the proposal says the slice stores nothing; do not create an empty placeholder or invent a schema to make a pair.
8. On the physical page, show the columns, types, nullability, defaults, keys, on-delete/on-update behavior, and indexes the proposal already lists. Represent named composite constraints and indexes in rows or keyed notes with ordered columns, not as independent column constraints. A status column uses the states in States and lifecycle; reference that section instead of copying the list into the diagram. A column or index the proposal lacks goes back to `design-data` first.
9. Mark personal or sensitive columns as the proposal does. Do not add audit, history, or soft-delete columns on the diagram.
10. Keep each **proposed** label and owner from the proposal. A blocking data question stays in Assumptions and open questions in `build-spec.md`, not only in a shape note.
11. Check each file against [Layout](references/erd-components.md#layout): exactly one page per file, unique cell ids on each page, row and cell parents, equal columns, every relationship between two rows, parents left of children, no line through a table, no shared segment, and every domain-model entity on its cluster's logical page. Zoom out: the main chain should still read left to right. Open each file in Draw.io or diagrams.net before claiming that it renders. If you could not open it, say so.

Link each generated file separately under Domain model in `build-spec.md` and under Information model in `technical-design.md` when that file exists, with its question. The domain model stays the source for attributes and relationships. The logical additions stay the source for identifiers, normalization, and the physical proposal. The diagrams reference them. The service contract stays in `technical-design.md`. Do not write SQL, migrations, or ORM code. The diagrams are **proposed**. They are not evidence that the schema performs, migrates safely, or meets a retention policy.

**Reply:** the separate file paths, the question, the entities and relationships, any external references, whether a physical file was drawn (or why it was omitted) and whose conventions it follows, the proposed physical choices with owners, the blocking data questions, and what the diagrams do not test.
