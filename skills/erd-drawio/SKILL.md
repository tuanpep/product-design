# ERD Draw.io

Read [principle-one-source-of-truth](../principle-one-source-of-truth/SKILL.md), [principle-design-every-state](../principle-design-every-state/SKILL.md), [principle-protect-before-you-enable](../principle-protect-before-you-enable/SKILL.md), [principle-spend-less-of-the-world](../principle-spend-less-of-the-world/SKILL.md), and [principle-decide-the-reversible](../principle-decide-the-reversible/SKILL.md). The diagram draws the domain model; it does not invent one. A physical schema is a proposal for builders, not a migration.

1. Name the question the diagram answers, for example: can a cover request exist without a shift? Read Glossary, Domain model, States and lifecycle, and Integrations and data in `build-spec.md`. If they do not exist, run `model-domain` first.
2. Write uncompressed XML in `docs/product-design/<slug>/`, following [the Draw.io file skeleton](../drawio/references/drawio-file.md) and [the ERD components](references/erd-components.md). One cluster of related entities keeps `erd.drawio`, with logical and physical as its two pages. A second cluster that shares no relationship with the first is `NN-<cluster>/erd.drawio`, numbered in the order the business needs the data, as [one file per close flow](../drawio/references/drawio-file.md#one-file-per-close-flow). Put it in the step folder when that step owns the entities.
3. **Logical page.** One entity per domain entity, named with its glossary term. List the key attributes the domain model names, marking the primary key (PK), foreign keys (FK), required or optional, and personal or sensitive data. Do not add types. An attribute or entity that the domain model lacks goes back to `model-domain` first, so the text stays the source.
4. Draw each relationship with crow's-foot ends that match the domain model's cardinality: exactly one, zero or one, one or many, zero or many. Label it with a verb from the glossary. When an entity relates to another twice, such as a requester and a colleague who are both staff, draw both relationships and name each role.
5. Resolve many-to-many relationships into an associative entity when the link carries its own attributes or lifecycle. Keep the logical model in third normal form. Record each deliberate exception and its reason in the note.
6. An entity whose system of record is another system is an external reference: draw it with the external style, and link it with the integration ID (I1) instead of a foreign key the product cannot enforce.
7. **Physical page.** Draw it only when the target project already has a database or the human asks for one. Inspect the existing schema, migrations, or ORM models first, and follow their naming, key type, timestamp, and soft-delete conventions. Mark each table existing, changed, or new. Never redraw an existing table differently from its source; mark a change as **proposed**.
8. For each table, give columns with type, nullability, default, and constraint: PK, FK with its on-delete behaviour, unique, and check. A lifecycle becomes a status column whose allowed values are the states in States and lifecycle; reference that section instead of repeating the list. Add an index only for a lookup, uniqueness, or ordering that a story or rule needs, and say which in the note.
9. For personal or sensitive columns, state the purpose, who can read them, and the proposed retention in the note. Do not add audit, history, or soft-delete columns unless a rule, a recovery path, or a retention requirement needs them. A column the outcome does not need is not kept.
10. Physical choices are reversible defaults: label them **proposed** with the reason and an owner. A choice that would lose or expose data on migration, or that touches money, law, or privacy, stays a blocking question in Assumptions and open questions in `build-spec.md`.
11. Check the file: unique cell ids on each page, every row's parent is its table and every cell's parent is its row, every row has the same columns, every relationship runs between two rows, no two relationships share a segment ([Edges do not overlap](../drawio/references/drawio-file.md#edges-do-not-overlap)), and every entity in the domain model appears on the logical page. Open it in Draw.io or diagrams.net before claiming that it renders. If you could not open it, say so.

Link the file under Domain model in `build-spec.md` with its question. The text in `build-spec.md` stays the source for entities, attributes, states, and rules; the diagram references them. Do not write SQL, migrations, or ORM code. The diagram is **proposed**. It is not evidence that the schema performs, migrates safely, or meets a retention policy.

**Reply:** the file path, the question, the entities and relationships, any external references, whether a physical page was drawn and whose conventions it follows, the proposed physical choices with owners, the blocking data questions, and what the diagram does not test.
