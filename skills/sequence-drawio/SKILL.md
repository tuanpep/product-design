# Sequence Draw.io

Apply [the shared execution contract](../design-product/references/specialist-execution.md). Principle links below are selective candidates, not mandatory preloads; read a leaf before citing it. Draw material interaction scenarios, not one sequence per operation by quota.

Relevant principles: [meaningful states](../principle-design-every-state/SKILL.md), [single ownership](../principle-one-source-of-truth/SKILL.md), and [predictable behavior](../principle-behave-predictably/SKILL.md). Draw an interaction `build-spec.md` already names; do not design the API here. Use [UML 2.5.1 sequence notation](https://www.omg.org/spec/UML/2.5.1/) with built-in UML shapes.

1. Name the question the diagram answers, for example: what does each person see when the roster update fails? Read Integrations and data, Business rules, States and lifecycle, and Quality requirements in `build-spec.md`, and the owning message catalogue in `screens.md`, or Product experience in the proposal without screen files. If the integrations are not described, run `model-domain` first.
2. Draw a sequence only when the order matters: an integration call, a notification, a handoff between people, a timeout, or a retry that a person can notice. A scenario with one actor and one screen is clearer as a journey.
3. Write uncompressed XML in `docs/product-design/<slug>/`, following [the Draw.io file skeleton](../drawio/references/drawio-file.md) and [the sequence components](references/sequence-components.md). One scenario keeps `sequence.drawio`. Each further scenario is `1-<step>/sequence.drawio`, one page, in the step folder of the journey it draws, as [one file per close flow](../drawio/references/drawio-file.md#one-file-per-close-flow).
4. Draw one lifeline per participant: the people involved, the product, and each other system with its integration ID. Put the starter on the left and people who are only told on the right, so most messages run left to right. One scenario per file.
5. Draw the messages top to bottom in the order they happen. Mark each as a call, an asynchronous message, or a return. Label each with what is asked or said and the ID it traces to: a screen (SC), a rule (BR), an integration (I), or a message (M).
6. For calls in the selected scenario, cover consequential failure, timeout and late-result outcomes in guarded `alt` paths, grouping equivalent cases without hiding material differences. Show what affected people are told and cite lifecycle effects only when the owner specifies them; failed reads may leave state unchanged, and stateless interactions need no invented lifecycle. Apply [the content truth check](../design-product/references/content-quality.md#check-business-truth-before-polishing): timeout does not prove nothing was saved, and acknowledgement is not completion. Reference M IDs; flag missing/stale copy rather than inventing a guarantee or safe retry.
7. Use `opt` for a step that may not happen and `loop` for a repeat with its limit. Cite the owning technical mechanism for commit, concurrency and duplicate handling. Do not invent atomicity, safe retries or delivery guarantees in a drawing. Missing timeout, retry or wait values can be proposed defaults only when reversible and nonblocking; behavior that could duplicate a consequential effect or violate an invariant remains an explicit blocker with an owner or Unknown. Record it in Assumptions and open questions.
8. Check against owning text: every participant is an actor, product or listed integration; every message ID exists; failure paths explain outcome, uncertainty and recovery, linking the unchanged/resulting lifecycle state only where applicable. Do not invent a failure state to close an interaction. Reconcile authorized differences in owning text first. Check unique cell IDs, messages between activation bars, horizontal lifeline messages and [relationship geometry](../drawio/references/drawio-file.md#relationship-lines). Claim rendering only after opening in Draw.io/diagrams.net; otherwise report it unverified.

Link the file under Integrations and data in `build-spec.md` with its question. The text in `build-spec.md` stays the source for integrations, rules, and states; the diagram references them. Do not write endpoint paths, payloads, or code. A sequence diagram is **proposed**. It does not test the other system's real behaviour, response times, or error codes.

**Reply:** the file path, the question, the participants, the failure and timeout paths drawn, the proposed timeouts and retries with owners, any difference found against `build-spec.md`, and what the diagram does not test.
