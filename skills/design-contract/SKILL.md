# Design Contract

Apply [the shared execution contract](../design-product/references/specialist-execution.md). Principle links below are selective candidates, not mandatory preloads; read a leaf before citing it.

Use [principle triggers](../design-product/references/principles.md) selectively: contract-first, standard methods, schema separation, testability, single ownership and realistic examples. The contract is the external schema. Callers, builders, and testers can implement against it. It is not server code, and it is not a copy of the screens or the tables.

1. Read Design views in `technical-design.md` and the stories, rules, and domain model in `build-spec.md`. If the interface view is omitted, stop. If those sources are missing, run the owning skill first.
2. Identify the authoritative existing contract, version, consumers and generation workflow before proposing changes. Keep package-root files as required below, but label whether they are proposed replacements, synchronized snapshots, or proposed changes and cite their source/version. Do not create a competing authority or claim compatibility from valid syntax. List resources from the tasks callers perform, using glossary terms. A resource exists when a caller can name one instance. Give it a relationship to its parent when the path needs one. Do not create a resource for every entity, and do not create one for every screen.
3. For each story or integration that crosses an HTTP boundary, add the operation that story needs. Prefer the standard methods: list and create on a collection, get, update, and delete on one resource. Use a custom operation when the action is a guarded transition, such as accept or cancel, and point it at the state and the rule. Give the operation an ID (OP1).
4. Write `openapi.yaml` at the package root. Use the OpenAPI 3 minor version the project already standardizes, citing `survey-existing` when it recorded one, or 3.1.0 when it does not. Include `info`, a relative `servers` URL, `paths`, and `components.schemas`. Each operation has an `operationId`, a summary, its parameters, a request body when it sends one, a success response with an example that uses realistic values, and an error response of `application/problem+json` as defined by [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html). Put `x-serves`, `x-rules`, and `x-entity` on the operation so the traces stay machine-readable.
5. A collection a story can grow without a known small bound needs a bounded retrieval design. Reuse established pagination; a new page size and continuation token are **proposed**, not a safe silent change to existing clients. For consequential writes, define commit/success meaning, ambiguous timeout recovery, safe retries, duplicate identity/scope and changed-parameter handling where applicable. An idempotency key is a proposed mechanism, not proof of atomic enforcement or protection from competing or stale requests. Cite invariant enforcement in the information/state views and flag unresolved correctness as blocking. Assess affected consumers' source, wire and semantic compatibility, including defaults, enum values and pagination.
6. Describe authentication with the scheme `survey-existing` recorded, or the scheme the project already uses when that survey did not run. When the scheme is unknown, omit a fake scheme, say so in Service contract, and add a question. If the operation reads or changes personal data, that question is blocking.
7. When a message is sent or received across the product boundary, write `asyncapi.yaml` for those channels only, using the project's supported version or an explicitly proposed tooling-compatible version. State the application's send/receive perspective; do not derive the opposite party by flipping direction. Describe applicable acknowledgments, duplicates, ordering, replay, retry exhaustion, recovery ownership and state/publication consistency, referencing the owning integration behavior. A schema establishes no delivery guarantee. Do not convert the HTTP file into events, invent messaging infrastructure, or emit an event for every state change unless a consumer story needs it. Point each message at its story and glossary term.
8. A contract field that renames, hides, or combines conceptual attributes states that mapping in Service contract. A field with no glossary term goes back to `model-domain` first. A field that copies a physical column name for its own sake is rewritten from the caller's task.
9. Check the files: every operation traces to a story, every error a rule can cause has a problem response, and examples match the schema. Identify applicable specification/reference resolution, schema/example, compatibility and implementation-conformance checks separately. Report which were actually performed, by whom/tool, on what version and with what limitations; otherwise mark planned/not performed. A restricted agent must hand off shell-based validation, not claim it ran. Do not write server stubs, client code, or SQL.
   Apply [the content truth check](../design-product/references/content-quality.md#check-business-truth-before-polishing) to consequential outcomes: distinguish accepted/pending work from confirmed completion, and a timeout from a known failure. Map these outcomes to existing M IDs in Correspondences without copying UI strings into the API schema. Flag missing or stale copy and unsafe retry advice; the technical handoff reconciles affected wording or reports the required follow-up.

Write the operation list under Service contract in `technical-design.md` using [the technical design format](../design-product/references/technical-design-format.md), and link the files. The YAML is **proposed**. It does not prove the service performs, authorizes correctly, or is safe to expose.

**Reply:** the resources, the operations and the stories they serve, any event channels, the mappings that are not one field to one attribute, the unknown authentication or limits, and what the contract does not implement.
