# Specialist execution and policy ownership

Applies to every task entry point, including direct calls. The default authoring path reads [the execution kernel](execution-kernel.md) and [active phase pack](phase-routing.md); use this detailed contract for scope/policy conflicts rather than compulsory full reading on every specialist call. Reuse unchanged references. A specialist owns its named output, not a new workflow or authority to approve it.

## Execute within the request

1. Establish target project/package, requested operation, open phase, output cap and named handoff from the request and existing package. Reuse applicable evidence, definitions, IDs and human edits. Do not restart completed discovery or modeling merely because another skill is called.
2. A direct specialist request is scoped work, not permission to complete later phases, raise the level, invent prerequisites or approve decisions. If it explicitly asks for a later phase, use the advance policy below; otherwise stay within the open phase. Throughout specialist procedures, "run the owning skill first" or "continue with" means only within the authorized scope, open phase and cap. Do not fill an omitted view, rerun an earlier phase or produce sibling artifacts automatically to satisfy a direct request. Reuse adequate supplied/authoritative input; otherwise report the missing prerequisite and affected work, asking only when the canonical policy requires it. Generic `drawio` and focused copy rewrites can operate on supplied material without creating a design package or opening a phase.
3. Before changing a fact, find its authoritative owner. Update that definition first and only affected authorized representations. Existing schemas/contracts and accepted decisions remain authoritative unless revision is explicitly in scope. Preserve IDs, unaffected content and decision history. An unknown is not permission to invent an expected outcome.
4. Standalone review is read-only. Authoring or explicit repair permits supported corrections within the request, not silent policy choices or fabricated human approval. Retain findings and recheck affected dependencies. If an update is outside scope, name the stale file/claim and next owner; do not claim package-wide consistency.
5. A blocker invalidates readiness for the affected handoff, not automatically for every learning action. In authorized revision withdraw dependent ready claims; in read-only review report them as invalid. Report performed versus planned checks and inaccessible material. Valid XML, schema or links establish structure, not semantics, feasibility, participant success or approval.
6. Keep protection, inclusion, meaningful boundary/recovery behavior, testable outcomes and single ownership even when no principle leaf is loaded. Load a leaf when it could change a choice, resolve a conflict, or support an explicit citation; read it before citing. Do not read all linked leaves merely because a skill lists them.

## One policy owner per concern

Load the relevant owner when its policy is needed; do not read this entire graph for every task. A specialist's procedure does not override these policies. Report an unresolved conflict rather than silently choosing a favorable rule.

| Concern | Canonical owner | When to load |
| --- | --- | --- |
| Discovery sufficiency, interview, advance requests | [Discovery policy](discovery-interview.md) | New brief, missing context or phase advance; explicit advance proceeds with unknowns, without another interview/confirmation |
| Phase sequence and gates | [Workflow](workflow.md) | Routing or gate decision; a level/advise alone does not open a phase |
| Levels, profiles, allowed artifacts and readiness | [Output standard](output-standard.md) | Creating/reviewing package outputs or interpreting a cap |
| Evidence labels and human decision authority | [Evidence contract](evidence-and-decisions.md) | Classifying claims or decisions |
| Synthesis, evaluation, supplied results and learning | [Learning loop](learning-loop.md) | Research or changed evidence; results ingestion uses [revision](../playbooks/revise-design.md), not a second synthesis procedure |
| Trade-off precedence | [Principles index](principles.md) | Principles conflict; leaf before explicit citation |
| Copy ownership, language and business truth | [Content contract](content-quality.md) | Writing/reconciling prose or service copy |
| Technical correctness and authoritative artifacts | [Technical format](technical-design-format.md#correctness-and-change-safety-review) | Technical work or a technical readiness claim |
| Review findings, repair and verdicts | [Review skill](../../review-design/SKILL.md) | Review/repair; do not run a second full review just to recommend the next action |

Use the owning format only for files actually needed. No new mandatory report, checklist document, artifact or phase is introduced by this contract.
