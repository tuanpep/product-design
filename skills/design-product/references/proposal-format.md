# Proposal format

Use these headings in `product-design.md`. Write concise prose or tables; omit inapplicable details with an explanation rather than filling space. Put evidence status next to consequential claims.

1. **Recommendation.** Proposed direction, the principle that decides the main trade-off and the principle it costs, reversal condition, and decision owner. Use [the principles](principles.md).
2. **Problem and outcome.** People, context, current experience, problem evidence, intended outcome, baseline if known, and measurement plan.
3. **Evidence and unknowns.** Source-linked observations, given context, inferences, assumptions, and the tests or owners for consequential gaps.
4. **Options.** Existing/no-build baseline, credible alternatives, comparison criteria, recommendation and rejected options.
5. **Product experience.** Entry and exit, main and exception journeys, user roles, content, information and rules, accessibility, service/support handoffs, data and system boundaries. Include only the details needed for the proposed scope.
6. **First useful release.** In/out scope, stories (who, what, and why), acceptance outcomes, behaviors and quality expectations, how each important behavior will be checked, transition or rollout implications, and measurable signals.
7. **Review and next steps.** Separate design coherence, evidence confidence, and delivery readiness. Name the next gate: stop, repeat discovery, test solutions, specify a slice, or ready for a named build slice. Identify unresolved contradictions, risks, next tests, and human decisions.
8. **Decision history.** Date, change in premise, prior decision, new decision and its status. On the first pass, record the initial recommendation.

Link each `.drawio` flow chart or prototype here, with the question it tests. A diagram is not a replacement for explaining its assumptions, branches, and evidence.
