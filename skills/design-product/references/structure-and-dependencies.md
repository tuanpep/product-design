# Shared structure and dependency procedure

Implementation trial shared by `design-composition` and `design-dependency`; both public entry points and section owners remain. Run this reasoning once when both views are included. Reuse completed sections when invoked separately. This is not evidence of improved host performance.

1. Read the included concerns and existing architecture/survey evidence. Reuse named parts, integration IDs and responsibilities. Do not infer that requesting one view includes the other or authorizes a new architecture.
2. Establish a single part inventory in **Composition** in `technical-design.md`: purpose, kind, owned/external boundary, built/bought/reused, existing/changed/new, and applicable evidence. If dependency work needs a missing part, propose it to this owner first. Do not populate an omitted view merely to satisfy a template; record the missing authoritative input and its consequence.
3. Record dependencies in **Dependencies** using those part names: direction (`A requires B`), shared interface/data/contract, reason and change impact. Reference external I IDs and their failure behavior rather than repeating it. Separate runtime dependencies from build/integration prerequisites; runtime call direction alone is not a build schedule.
4. Detect cycles. Name the mutually dependent group and effects on testing, rollout, consistency and change coupling. An acyclic prerequisite graph permits an order; a cycle needs a justified integration increment, shared contract/test boundary or investigation. Do not invent a topological order or remove a real cycle for presentation. A runtime cycle can coexist with an acyclic implementation plan; explain the distinction.
5. Resolve only reversible local choices as proposed defaults with owner/reason. Significant compatibility, security, platform or operational choices use `record-decisions`; unresolved blocking choices stay questions. An existing reusable part is not replaced without evidence and an authorized decision.
6. Reconcile only affected concerns and owning sections. Composition owns responsibilities and the optional containers page; Dependencies owns coupling/change impact and proposed integration order; integrations own external failure behavior; deployment owns environment/transition/recovery. Do not add a second context or dependency diagram by default.

Report what changed, reused inputs, cycles and their implications, proposed order/limitations and unresolved owners. Readiness follows the shared execution/output contracts, not the presence of two filled tables.
