# Mockup Draw.io

This skill produces the complete canonical screen/state handoff, not every early research material. Check the proposal's optional Level header: understand and design-documents forbid canonical screens and mockups; mockup and full allow them, subject to the profile. Absence retains legacy behavior. Do not silently raise the level. Establish the Evaluation plan and risky question before making artifacts. Small inline proposal examples or linked external materials can support early learning without forcing `screens.md` or `mockup.drawio`; see [GOV.UK alpha guidance](https://www.gov.uk/service-manual/agile-delivery/how-the-alpha-phase-works). Those materials do not replace this skill's complete handoff when it is required.

Read [principle-use-real-content](../principle-use-real-content/SKILL.md), [principle-design-every-state](../principle-design-every-state/SKILL.md), and [principle-behave-predictably](../principle-behave-predictably/SKILL.md). The mockup should look like the product people will use, so they can judge layout, content, and states. It is still a proposal, not a built screen.

## Fit the artifact to the question

Declare visual, content, and interaction fidelity separately. This skill supplies high-fidelity visuals and realistic content, but static interaction with annotated flows. Arrows document transitions; they do not implement clicks, typing, validation, timing, keyboard behaviour, or assistive-technology semantics. Draw.io supports interactive links/layers and animations, but this skill deliberately does not use those mechanisms. Do not call this output interactive or production-ready. “Mockup” is our local naming convention, not a universal ban on the research term “static prototype.”

For early learning, choose the smallest material capable of answering the question rather than polishing a complete handoff prematurely. Static frames can support discussion of hierarchy or wording; a prepared human-operated sequence can support scoped task observation. Real input, conditional branching, responsive behaviour, keyboard use, or screen-reader questions need an appropriately implemented interactive artifact, owned externally. Record that dependency in the Evaluation plan instead of claiming these static frames answer it or silently expanding into code generation. See [the research basis and method boundaries](references/mockup-research.md).

## Build the complete handoff

1. Name the question the mockup is intended to investigate, not an answer already established. Link the relevant assumption and planned support/weaken/reverse criteria in the Evaluation plan. Read `screens.md`, the owning source for screens and copy, and draw only the screens and states it lists. If it does not exist, run `design-screens` first, subject to the output level. Resolve missing recoveries, transitions, or responsive variants in `screens.md` before drawing; do not invent behaviour in XML.
2. Inspect the target project for an existing UI, design system, or tokens. Match its layout, navigation, colours, font, and corner radius. Otherwise use the **Carbon-informed White default** in [the component library](references/web-components.md), including its [extended component recipes](references/extended-components.md). Keep the theme, layer, density and button hierarchy consistent across all components. Say which tokens are used in the frame notes, including any portable-font substitution; these static shapes are not executable Carbon components.
3. Choose the device from the context of use: desktop browser, tablet, or mobile. Use the same device for every frame unless the slice is responsive, then draw the hardest one first.
4. Write uncompressed XML in `docs/product-design/<slug>/`, following [the Draw.io file skeleton](../drawio/references/drawio-file.md). One actor and one task keep `mockup.drawio`. A second task, or a second actor doing a different task, is a step folder, `1-nurse-ask-cover/mockup.drawio`, as [one file per close flow](../drawio/references/drawio-file.md#one-file-per-close-flow). Use the same folder as the journey for that step. Caption the file `Actor · Task`. Draw each screen of that task once, in this actor's file. A second actor who only has less access to this task is a denied or read-only state here. End at the handoff, and start the other actor's file at what they receive. Inside a file, one row per screen in task order, one frame per state, left to right, with a caption above and a note below. A happy path longer than 6 screens splits at the next handoff into a child folder, `1.1-<step>/`; the state frames stay with their screen.
5. Build every frame from [the component library](references/web-components.md): only the chrome and components the task needs, followed by a clear page heading and relevant content. Use its base style recipes and explicitly adapt tokens to the target project. Do not add components just to display the kit, invent stencil names, or mistake drawn controls for implemented web components.
6. Name cells so they trace to the spec: the frame is `SC2-denied`, its children start with `SC2-denied-`. Every screen has at least a `-default` frame.
7. Put real content in every control: the words from `write-content`, plausible fictional data, the longest name, the empty list, and the denied message. Name each button by its action. Reuse fictional records across states; check dates, totals, counts, units, and statuses for consistency. Never put credentials or personal production data in the diagram. Do not shrink text to hide long-content problems; show the specified wrapping, truncation, or scrolling.
8. Draw the error, empty, loading, and denied states that `screens.md` lists, with the recovery visible. Show a denied state with the message ID and rule ID in the note.
9. Connect frames with flow arrows from the control the user acts on to the frame that follows, labelled with the action, following [Lines](../drawio/references/drawio-file.md#lines). A path the product shows is solid, including empty, error, and denied. When nobody acts, the label starts with `System:` and the source is the frame. A dashed arrow is only a layout option. A same-row arrow uses the column gap and enters on the left. An arrow to the next row uses the row gap and enters on the top.
10. Check the file: every cell id is unique, every arrow has an existing source and target, nothing overlaps or clips inside a frame, and no two arrows share a segment or cross ([Edges do not overlap](../drawio/references/drawio-file.md#edges-do-not-overlap)). Reconcile the frames against every screen/state in `screens.md` across all task files. Walk the happy path, recovery paths, back/cancel, and actor handoffs against the spec; flag unexplained dead ends. Open it in Draw.io or diagrams.net before claiming that it renders. If you could not open it, say so. XML validation alone does not verify layout.
11. Inspect accessibility design intent: visible labels and instructions, text rather than colour alone for status/errors, readable contrast, usable target spacing, and visible recovery. Keep keyboard/focus order, modal focus return, and status-announcement requirements in `screens.md`; frame notes link to them, not a second specification. Use [the component accessibility guidance](references/web-components.md#accessibility-and-viewport-intent). A drawing cannot verify those behaviours or WCAG conformance.

## Describe and prepare its use

Link the file under Product experience in `product-design.md`, with a compact brief: question/assumption, actor and task, entry frame and starting conditions, device/viewport, visual-style source, fidelity by dimension, fictional-data premise, and limitations. Reuse the existing Evaluation plan for method and decision criteria; do not create a parallel research plan. State what it does not test: no real interaction or live data, no responsive behaviour beyond the frames drawn, and no accessibility conformance or usability result. Mark board notes as design annotations, not product copy.

If the frames will be used for participant research, prepare a facilitator handoff under the Evaluation plan: a believable goal-based task that does not name the controls to use; starting data and reset conditions; a mapping from anticipated actions to frame IDs using specified transitions; treatment of unprepared actions; and observable task completion. Present only the current frame, not arrows, annotations, or future states that reveal the answer. Ask what the participant expected for unsupported actions rather than steering them to the intended control. Record assistance, frame-switch mistakes, and simulated delays as limitations, not product findings or real task timings. Request a pilot walkthrough before sessions; mark it planned until actually reported. Recruitment, consent, execution, and results remain external.

Keep every screen and designed state in `screens.md` covered across the mockup files; early learning's smaller scope does not relax this handoff contract. If supplied research results inform a revision, record their source, observations separately from interpretation, support/weakening/reversal and limitations under the proposal's existing Evaluation plan heading, then update the decision and affected frames. Opening a diagram does not supply research evidence.

**Reply:** the file path, the question, the device/viewport, the screens and states drawn, whose visual style it follows, fidelity by dimension, checks actually performed (including whether it was opened), and what it does not test or requires externally.
