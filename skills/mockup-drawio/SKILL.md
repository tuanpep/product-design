# Mockup Draw.io

This skill produces the complete canonical screen handoff: every screen and every declared **Views:** snapshot in `screens.md`, including consequential branches and role handoffs. It does not produce early learning material. A learning prototype is an inline concept, task, or scenario in the proposal, or a link to external material, and it must not be saved as `screens.md` or `mockup.drawio`. See [Learning material is not the complete screen handoff](../design-product/references/learning-loop.md#learning-material-is-not-the-complete-screen-handoff). If the question can be answered without this handoff, do not run this skill.

Check the proposal's optional Level header: understand and design-documents forbid canonical screens and mockups; mockup and full allow them, subject to the profile. Absence retains legacy behavior. Do not silently raise the level. Establish the Evaluation plan and risky question before making artifacts.

Read [principle-use-real-content](../principle-use-real-content/SKILL.md), [principle-design-every-state](../principle-design-every-state/SKILL.md), and [principle-behave-predictably](../principle-behave-predictably/SKILL.md). The mockup should look like the product people will use, so they can judge layout, content, and states. It is still a proposal, not a built screen.

## Fit the artifact to the question

Declare visual, content, and interaction fidelity separately. This skill supplies high-fidelity visuals and realistic content, but static interaction with annotated flows. Arrows document transitions; they do not implement clicks, typing, validation, timing, keyboard behaviour, or assistive-technology semantics. Draw.io supports interactive links/layers and animations, but this skill deliberately does not use those mechanisms. Do not call this output interactive or production-ready. “Mockup” is our local naming convention, not a universal ban on the research term “static prototype.”

These frames can support discussion of hierarchy or wording, and a person can operate a prepared sequence for scoped observation. They do not answer questions about real input, conditional branching, responsive behaviour, keyboard use, or screen readers. Record that dependency in the Evaluation plan. Do not generate code. See [the research basis and method boundaries](references/mockup-research.md).

## Build the complete handoff

1. Name the question the mockup is intended to investigate, not an answer already established. Link the relevant assumption and planned support/weaken/reverse criteria in the Evaluation plan. Read `screens.md`, the owning source for screens and copy. If it does not exist, run `design-screens` first, subject to the output level. Draw one frame per declared **Views:** entry, and one per legacy **States:** entry until that list is revised in the owning spec. Specify missing transitions, recoveries, and narrow-screen treatment in `screens.md` (Layout, Actions, Technical behavior) before drawing. Do not add a frame for behaviour that stays in that prose. A specified outcome, such as the saved collection in [collection-screens.md](references/collection-screens.md), is not a frame unless it is a declared view. Do not invent behaviour in XML.
2. Inspect the target project for an existing UI, design system, or tokens. Match its layout, navigation, colours, font, and corner radius. Otherwise use the **Carbon-informed White default** in [the component library](references/web-components.md), including its [extended component recipes](references/extended-components.md). Keep the theme, layer, density and button hierarchy consistent across all components. Say which tokens are used in the frame notes, including any portable-font substitution; these static shapes are not executable Carbon components.
3. Choose the device from the context of use: desktop browser, tablet, or mobile. Use the same device for every frame unless the slice is responsive, then draw the hardest one first.
4. Write uncompressed XML in `docs/product-design/<slug>/`, following [the Draw.io file skeleton](../drawio/references/drawio-file.md). Place files by this order:
   - One close flow (one actor, one task, one entry): `mockup.drawio` in the package folder. Caption it `Actor · Task`.
   - A second actor or a second task: the next parent step folder, `1-<actor>-<task>/mockup.drawio`, sharing that step's journey folder. Parents are `1`, `2`, `3` with no gaps.
   - Split only when the happy path would need more than 6 screens. Count screens, not every view. State frames of those screens stay in the same file. Nest the continuation inside the parent, `1-<step>/1.1-<substep>/mockup.drawio`, at the next handoff. Do not put the child beside the parent.
   - End this file at the handoff. Start the receiving actor's file at the named input. Keep parallel work parallel in the overview; do not invent a sequence. Keep setup and post-completion support out of the daily-task file.
   Order business views left to right, then top to bottom, as declared in `screens.md`. Draw approval, receiving, review, confirmation, follow-up, and completion where the task needs them. Keep important branches next to the decision they follow.
5. Read only what the frames need, in this order: the UI baseline and **Layout** archetypes in `screens.md`, the matching archetype and the principle table in [product-layouts.md](references/product-layouts.md), then the component sections those screens use in [web-components.md](references/web-components.md) and [extended-components.md](references/extended-components.md). Build every frame from those recipes: only the chrome and components the task needs, with the page title stating the action and the committing control after the content it commits. Adapt tokens to the target project. Do not add components just to display the kit, invent stencil names, or mistake drawn controls for implemented web components. Do not arrange a frame into an F-shape or a Z-shape.
6. Name cells so they trace to the spec: the frame is `SC2-awaiting-approval`, its children start with `SC2-awaiting-approval-`. Use the exact descriptive view names in `screens.md`; each screen retains a `-default` entry frame. Do not use a view name that prefixes another view name of that screen, or ends in reserved `-caption` / `-note`.
7. Put real content in every control that the declared views show: the words from `write-content`, plausible fictional data, and the longest name the layout must survive. Include an empty list or a denied message only when that view is declared or the message is in-frame product copy on a declared view. Name each button by its action. Reuse fictional records across states; check dates, totals, counts, units, and statuses for consistency. Never put credentials or personal production data in the diagram. Do not shrink text to hide long-content problems; show the specified wrapping, truncation, or scrolling.
8. Do not generate an empty/loading/partial/error/denied/success/offline matrix. Shared technical feedback belongs in concise specification notes. Draw a technical exception only if it changes the business decision, risk, next action, recovery, or handoff, or the user explicitly requests detailed UI states. Retain material rejection, withdrawal, unmet-prerequisite, and unresolved-result branches. If a legacy States list already exists, reconcile it with the owning specification before removing frames; never silently drop declared coverage.
9. Connect frames with flow arrows from the control the user acts on to the frame that follows, labelled with the action, following [Lines](../drawio/references/drawio-file.md#lines). A path the product shows is solid, including empty, error, and denied. When nobody acts, the label starts with `System:` and the source is the frame. A dashed arrow is only a layout option. A same-row arrow uses the column gap and enters on the left. An arrow to the next row uses the row gap and enters on the top.
10. Check the file: every cell id is unique, every arrow has an existing source and target, and no two arrows share a segment or cross ([Edges do not overlap](../drawio/references/drawio-file.md#relationship-lines)). Reconcile frames against every declared view across all task files. Walk the happy path, recovery paths, back/cancel, and actor handoffs against the spec; flag unexplained dead ends. Passing `npm test` or well-formed XML does not verify wrapping, alignment, clipping, or contrast. Claim a visual check only after the file is opened in Draw.io, diagrams.net, or the Draw.io editor. Otherwise report rendering as unverified.
11. Inspect accessibility design intent: visible labels and instructions, text rather than colour alone for status/errors, readable contrast, usable target spacing, and visible recovery. Keep keyboard/focus order, modal focus return, and status-announcement requirements in `screens.md`; frame notes link to them, not a second specification. Use [the component accessibility guidance](references/web-components.md#accessibility-and-viewport-intent). A drawing cannot verify those behaviours or WCAG conformance.

## Describe and prepare its use

Link the file under Product experience in `product-design.md`, with a compact brief: question/assumption, actor and task, entry frame and starting conditions, device/viewport, visual-style source, fidelity by dimension, fictional-data premise, and limitations. Reuse the existing Evaluation plan for method and decision criteria; do not create a parallel research plan. State what it does not test: no real interaction or live data, no responsive behaviour beyond the frames drawn, and no accessibility conformance or usability result. Mark board notes as design annotations, not product copy.

Prepare a facilitator handoff only when the person asked to use these frames with participants. Otherwise stop after the product-experience brief. When they did ask, add it under the Evaluation plan: a believable goal-based task that does not name the controls to use; starting data and reset conditions; a mapping from anticipated actions to frame IDs using specified transitions; treatment of unprepared actions; and observable task completion. Present only the current frame, not arrows, annotations, or future states that reveal the answer. Ask what the participant expected for unsupported actions rather than steering them to the intended control. Record assistance, frame-switch mistakes, and simulated delays as limitations, not product findings or real task timings. Request a pilot walkthrough before sessions; mark it planned until actually reported. Recruitment, consent, execution, and results remain external.

Coverage of every declared view is the handoff contract. A smaller learning stimulus belongs in the proposal, not in a partial `mockup.drawio`. If supplied research results inform a revision, record their source, observations separately from interpretation, support/weakening/reversal and limitations under the proposal's existing Evaluation plan heading, then update the decision and affected frames. Opening a diagram does not supply research evidence.

**Reply:** the file path, the question, the device/viewport, the screens and states drawn, whose visual style it follows, fidelity by dimension, checks actually performed (including whether it was opened), and what it does not test or requires externally.
