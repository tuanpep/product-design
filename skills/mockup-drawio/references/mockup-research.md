# Research basis for the mockup skill

Sources consulted 2026-10-15. These are published method/design guidance, not evidence that a particular product is usable. Applications below are repository-specific recommendations that preserve the complete Draw.io handoff and output-level constraints.

| Source | Relevant guidance | Application here |
| --- | --- | --- |
| [NN/g: UX Deliverables: A Glossary](https://www.nngroup.com/articles/ux-deliverables-glossary/) (2024-08-09) | A mockup is “A static, high-fidelity simulation of a proposed UI design that includes visual-design details such as colors and imagery.” A wireflow combines wireframe-style layouts with a simplified flowchart. | Name our detailed screen/state artifact a mockup with annotated flows; do not confuse transition arrows with working interaction or call detailed product-styled frames wireframes. |
| [NN/g: Wireflows](https://www.nngroup.com/articles/wireflows/) | One task per flow. Lay screens in usage order. Start each arrow on the control the person uses. The next node may be the same screen with changed content. A large desktop step may show only the region that changed. | One actor and one task per file. Business order, left to right then top to bottom. The arrow starts on the control. A changed screen is a new frame of that screen. Keep the full frame. Do not crop to the region that changed. |

| [Draw.io: Interactive diagrams with custom links and layers](https://www.drawio.com/docs/tutorials/interactive-diagram-layers/) and [Custom link actions](https://www.drawio.com/blog/custom-link-actions/) | Draw.io supports custom links, layers, page navigation, and animations. | Static output is this skill's deliberate scope, not a limitation of Draw.io. | [GOV.UK: Making prototypes](https://www.gov.uk/service-manual/design/making-prototypes) | Choose the prototype that meets current needs and use code for realistic web interactions. ## What each medium can support

“Mockup” is the repository's local convention for its static high-fidelity screen/state handoff with annotated flows. It is not a universal ban on “static prototype”: the NN/g fidelity article above allows static prototypes operated by a human. Learning prototypes and externally owned interactive artifacts remain valid research terms. Draw.io itself can be interactive; this skill produces static frames without interactive link/layer/page-navigation or animation mechanisms.

| Question | Appropriate material | Boundary |
| --- | --- | --- |
| Do people understand wording or hierarchy? | Realistic static frames shown in context, with an appropriate research procedure | A reviewer's opinion is inspection, not observed user success. |
| Can people find a route and recover from an error? | Prepared human-operated frame sequence for scoped early observation, or an interactive prototype | Arrows alone do not make a task test. Hide future frames; report assistance and simulation limitations. |
| Does validation work with varied input or preserve entered data? | Interactive implementation with relevant inputs and state | Static error frames describe intent, not a working validator. |
| Does the UI work with keyboard, screen reader, zoom, and reflow? | Appropriately implemented artifact tested with relevant technology and people | Focus and announcement notes are requirements, not results. Separate viewport drawings do not prove responsive behaviour. |
| Is there demand, operational feasibility, or production readiness? | Appropriate discovery, operational, engineering, or live-service evaluation | Visual polish and successful prototype tasks do not establish these claims. |

The complete screen/state handoff and one-file-per-close-flow arrangement are local artifact contracts, not requirements imposed by these sources. Small early research materials do not replace that handoff, and a complete handoff does not require testing every frame in one research session.

## Component-kit research

The [web UI kit](web-components.md#research-and-scope) records its source-to-component mapping for Ant Design, WAI-ARIA modal behaviour and WCAG target sizing. Its [example scenario](example-screens.md) owns the fictional records, state intent and accessibility requirements behind the editable diagram. The kit is a drawing reference, not an implementation of standards-compliant React components.

On 2026-10-23, the [Ant Design light baseline](web-components.md#extended-recipes-and-ant-design-styling) and [extended recipes](extended-components.md) replaced the previous component styling across all three Draw.io boards. Official component/theme pages and pinned `antd@6.6.7` sources informed the migration. Existing project tokens/version still take precedence. The [specimen board](component-recipes.drawio) is a reference, not a product flow. Arial is a portable system-stack fallback; retained48-high controls are local, not Ant's default32 or large40. Explicit contrast adaptations are recorded separately from library defaults. Static menus and suggestions establish no keyboard access or focus behavior.

Component-specific changes matter: blue primary actions, radius6 fields/buttons, radius8 cards, radius4 bordered Tags, blue selected navigation/radios, and tinted bordered error Alert. Collapse uses leading right/down caret with a locally divided ghost treatment. Dropdown now maps to an action Menu and explicitly uses click trigger; it is not a form Select. AutoComplete permits text and suppresses empty suggestions; active suggestion differs from committed selection, and prior Escape/Tab contracts are not inherited. Invalid DD/MM/YYYY deliberately remains Input text with application validation; DatePicker/TimePicker are custom Ant pickers, not native date controls. Upload is a real component mapping with pre-transfer checks; Descriptions plus Change links composes review. The source map and limitations remain self-contained in [web-components.md](web-components.md#research-and-scope), including default-token contrast gaps rather than a blanket accessibility claim.
