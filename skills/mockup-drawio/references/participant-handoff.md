# Optional participant handoff for static frames

Load only when asked to use these frames with participants. Otherwise stop after the Product experience brief. Reuse the existing Evaluation plan rather than a parallel research document.

- Give a believable goal-based task without naming controls. Define starting data/reset conditions, mapping from anticipated actions to frame IDs using specified transitions, handling of unprepared actions and observable completion.
- Show only the current frame, not arrows, notes or future states that reveal answers. For unsupported actions ask what the participant expected, rather than steering toward the intended control.
- Record assistance, frame-switch mistakes and simulated delays as method limitations, not product findings or real task timings. Request a pilot walkthrough before sessions, marked planned until reported. Recruitment, consent, execution and results remain external.
- Declare visual/content/interaction fidelity separately. These are static high-visual-fidelity frames with realistic content and annotated flows, not implemented clicks, typing, validation, timing, keyboard or assistive-technology semantics. Do not call arrows interactive or output production-ready. Draw.io's link/layer/animation mechanisms are deliberately not used here.
- Discussion of hierarchy/wording or a facilitated sequence can supply scoped observations if actually performed. It cannot establish behavior for real input, conditional branches, responsive layouts, keyboard use or screen readers. Record that dependency in Evaluation plan; do not generate code.

When actual results are supplied, use [the learning loop](../../design-product/references/learning-loop.md): provenance, observations separate from interpretation, criteria comparison and limitations. Revise the affected decision and frames only within authorization. Opening a diagram supplies no participant evidence. See [research basis and boundaries](mockup-research.md).
