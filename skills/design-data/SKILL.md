# Design Data

Apply [the shared execution contract](../design-product/references/specialist-execution.md). Principle links below are selective candidates, not mandatory preloads; read a leaf before citing it.

Use [principle triggers](../design-product/references/principles.md) selectively: logical clarity, schema separation, single ownership, lifecycle, protection, retained-data cost and reversible defaults. This is the information view's text. `erd-drawio` draws it. `design-contract` does not copy it. Do not write SQL, migrations, or ORM code.

1. Check Design views first; if information is omitted, stop without changing prerequisites. Read Glossary, Domain model, States and lifecycle, Business rules and Stories in `build-spec.md`. If a required conceptual premise is missing, identify its `model-domain` owner and bound/defer affected work; do not invent it or silently rerun Specify.
2. **Logical model.** One entry per conceptual entity, using the glossary name. Cite the domain-model entry for its purpose, each attribute's meaning, whether it is required, its example, its allowed values, and whether it is personal or sensitive. Do not restate that prose. Add only the primary identifier and any alternate business key. Do not assign a database type.
3. Cite each relationship from the domain model, including a second role such as requester and colleague. The domain model owns the cardinality, read both ways: exactly one, zero or one, one or many, or zero or many. If a relationship cannot be read both ways, fix that sentence in the domain model. Do not copy it here.
4. Put the model in third normal form. An attribute holds one value, not a list. An attribute depends on the whole primary identifier. A fact that depends on another non-key attribute moves to the entity that owns it. A many-to-many link that has its own attributes or lifecycle becomes an associative entity. When that move changes an attribute or a relationship, change the domain model first, then record the exception here: the update anomaly it accepts, the story that forces it, and its owner. Copying personal data into that exception is blocking.
5. An entity stored in another system is an external reference. Cite its integration ID. Do not give this product a foreign key it cannot enforce. When a surrogate identifier is proposed, keep the business key as an alternate identifier.
6. **Physical proposal.** Write it when the slice needs new or changed persistence, an unresolved internal-schema concern, or the human asks for a schema. Apply [the physical database design standard](references/database-standard.md) when writing it. Use English for authored physical metadata and new identifiers; preserve existing identifiers and externally governed codes exactly, with English explanations. The mere existence of a project database does not require redesigning it. For unchanged storage, cite the applicable authoritative schema and explain reuse; distinguish unchanged reuse from a new physical proposal. When the survey did not run, inspect the relevant schema, migrations, or ORM models. Follow their names, key types, timestamps, and delete conventions. Mark each table existing, changed, or new. Never restate an existing table differently from its source.
7. Name the target database product and version. For each new or changed column, give a concrete engine type with applicable length/precision/scale, nullability, default or none, generation strategy, and constraints. Name composite keys and constraints with their ordered columns. A lifecycle is a status column whose allowed values are the states already listed; reference that section. Choose on-delete from the lifecycle: restrict when a rule or history must keep the parent, and a proposed cascade only when the child has no meaning without the parent and no rule keeps it. Record on-update behavior too. When the database product is unknown, name a type family and an owner, label the proposal engine unresolved, and do not claim implementation readiness. Do not name a product as if it had been observed.
8. Include engine-required supporting indexes without duplicating indexes the engine already creates. Review each foreign key for lookup, join, and parent update/delete cost; record an index or the reason for omitting it. Add other indexes only for a lookup, a uniqueness rule, or an order a story states, and cite that story or rule. Give index names, ordered keys, and any predicate or included columns. Do not add audit, history, or soft-delete columns unless a rule, a recovery path, or a retention requirement needs them.
9. For each personal or sensitive column, cite the domain model's purpose, reader, and retention. Do not restate them. A column the outcome does not need is dropped. A physical choice that would lose or expose data on migration stays a blocking question in Assumptions and open questions. Other physical choices are **proposed** defaults with owners.
10. Reference consequential business invariants and name the authoritative state owner, enforcement/transaction boundary, uniqueness or conditional-update mechanism, and checks for competing/stale writes where relevant. Duplicate-request handling alone does not enforce cross-request invariants. For changed persistence, describe old/new coexistence, backfill/validation, cutover/cleanup and interrupted-transition recovery; link the owning rollout plan. Do not assume application rollback restores data or reverses external effects. Unresolved consequential enforcement or transition safety remains blocking; no migration code is generated.
11. Then `erd-drawio` draws `erd-logical.drawio`, and a separate `erd-physical.drawio` when this skill wrote a physical proposal. Each file has one page; never combine the views. A difference in an attribute or a relationship is fixed in the domain model first. A difference in an identifier, a normalization note, or a physical column is fixed in this text first.

Write the identifiers, normalization result, and any physical proposal under Information model in `technical-design.md`, using [the technical design format](../design-product/references/technical-design-format.md). Each entry names the entity and links to its domain-model entry. When that file does not exist, add only those logical notes after the conceptual entry in Domain model and say they are not a second copy of the attributes. Link `erd-logical.drawio` and, when drawn, `erd-physical.drawio` separately. The text is **proposed**. It does not show that the schema performs, migrates safely, or meets a retention policy.

**Reply:** the entities and their identifiers, the domain-model entries cited, any normalization exception and its anomaly, whether a physical proposal was written and which existing conventions it follows, the proposed defaults and blocking data questions, and what this design does not prove.
