# Design Data

Read [principle-settle-the-logical-model](../principle-settle-the-logical-model/SKILL.md), [principle-keep-the-schemas-apart](../principle-keep-the-schemas-apart/SKILL.md), [principle-one-source-of-truth](../principle-one-source-of-truth/SKILL.md), [principle-design-every-state](../principle-design-every-state/SKILL.md), [principle-protect-before-you-enable](../principle-protect-before-you-enable/SKILL.md), [principle-spend-less-of-the-world](../principle-spend-less-of-the-world/SKILL.md), and [principle-decide-the-reversible](../principle-decide-the-reversible/SKILL.md). This is the information view's text. `erd-drawio` draws it. `design-contract` does not copy it. Do not write SQL, migrations, or ORM code.

1. Read Glossary, Domain model, States and lifecycle, Business rules, and Stories in `build-spec.md`. If the conceptual model is missing, run `model-domain` first. If Design views omits the information viewpoint, stop.
2. **Logical model.** One entry per conceptual entity, using the glossary name. Cite the domain-model entry for its purpose, each attribute's meaning, whether it is required, its example, its allowed values, and whether it is personal or sensitive. Do not restate that prose. Add only the primary identifier and any alternate business key. Do not assign a database type.
3. Cite each relationship from the domain model, including a second role such as requester and colleague. The domain model owns the cardinality, read both ways: exactly one, zero or one, one or many, or zero or many. If a relationship cannot be read both ways, fix that sentence in the domain model. Do not copy it here.
4. Put the model in third normal form. An attribute holds one value, not a list. An attribute depends on the whole primary identifier. A fact that depends on another non-key attribute moves to the entity that owns it. A many-to-many link that has its own attributes or lifecycle becomes an associative entity. When that move changes an attribute or a relationship, change the domain model first, then record the exception here: the update anomaly it accepts, the story that forces it, and its owner. Copying personal data into that exception is blocking.
5. An entity stored in another system is an external reference. Cite its integration ID. Do not give this product a foreign key it cannot enforce. When a surrogate identifier is proposed, keep the business key as an alternate identifier.
6. **Physical proposal.** Write it when Design views includes the internal schema, the project already has a database, or the human asks for a schema. Otherwise say why this slice stores nothing and skip it. Cite the schema `survey-existing` recorded. When that survey did not run, inspect the existing schema, migrations, or ORM models. Follow their names, key types, timestamps, and delete conventions. Mark each table existing, changed, or new. Never restate an existing table differently from its source.
7. For each new or changed column, give a type family, nullability, default, and constraint: primary key, foreign key, unique, or check. A lifecycle is a status column whose allowed values are the states already listed; reference that section. Choose on-delete from the lifecycle: restrict when a rule or history must keep the parent, and a proposed cascade only when the child has no meaning without the parent and no rule keeps it. When the database product is unknown, name a type family and an owner. Do not name a product as if it had been observed.
8. Add an index only for a lookup, a uniqueness rule, or an order a story states, and cite that story or rule. An index on a foreign key is a proposed default only when a story lists children by that parent. Do not add audit, history, or soft-delete columns unless a rule, a recovery path, or a retention requirement needs them.
9. For each personal or sensitive column, cite the domain model's purpose, reader, and retention. Do not restate them. A column the outcome does not need is dropped. A physical choice that would lose or expose data on migration stays a blocking question in Assumptions and open questions. Other physical choices are **proposed** defaults with owners.
10. Then `erd-drawio` draws the logical page, and the physical page when this skill wrote one. A difference in an attribute or a relationship is fixed in the domain model first. A difference in an identifier, a normalization note, or a physical column is fixed in this text first.

Write the identifiers, normalization result, and any physical proposal under Information model in `technical-design.md`, using [the technical design format](../design-product/references/technical-design-format.md). Each entry names the entity and links to its domain-model entry. When that file does not exist, add only those logical notes after the conceptual entry in Domain model and say they are not a second copy of the attributes. Link `erd.drawio` after it is drawn. The text is **proposed**. It does not show that the schema performs, migrates safely, or meets a retention policy.

**Reply:** the entities and their identifiers, the domain-model entries cited, any normalization exception and its anomaly, whether a physical proposal was written and which existing conventions it follows, the proposed defaults and blocking data questions, and what this design does not prove.
