# Frame Problem

Apply [the discovery interview and context gate](../design-product/references/discovery-interview.md). Reuse known facts and ask focused open questions for core gaps rather than inventing a problem behind the requested feature. Stay in Understand until the gate passes.

Read [the evidence contract](../design-product/references/evidence-and-decisions.md) and [principle-start-from-the-outcome](../principle-start-from-the-outcome/SKILL.md).

1. Restate the request as the people affected, what they are trying to achieve, how they do it today if that is known, the intended outcome, and the proposed feature if one was supplied.
2. Keep the feature distinct from the need. State what is not part of the problem.
3. Set a discovery goal first: the decision this work must support, its uncertainty, and how you will know the framing is finished. Name the decision owner when known. Otherwise mark the owner unknown.
4. Separate the user outcome from the business/service outcome and explain their proposed connection or conflict. Record baseline/source when available; do not invent metrics. Follow [the learning loop](../design-product/references/learning-loop.md) from this framing through synthesis, opportunity selection, and evaluation.

Do not compare solutions, specify an interface, or treat the original feature as the requirement. A stakeholder's request is **given**, not an observed user need.

**Reply:** the problem, the people, the outcome, the proposed feature kept separate, and the discovery goal.
