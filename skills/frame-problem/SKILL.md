# Frame Problem

Load [the shared execution contract](../design-product/references/specialist-execution.md) only for a direct call without an owner, or a scope/policy conflict. Prefer the owner's kernel and active pack. Principle links below are selective candidates, not mandatory preloads; read a leaf before citing it.

Reuse known facts. Ask focused open questions for core gaps only when no advance was requested; [discovery policy](../design-product/references/discovery-interview.md) owns exact advance semantics. An explicit advance leaves Understand with unknowns recorded, without another interview or confirmation; do not invent a problem behind the requested feature.

Load [the evidence contract](../design-product/references/evidence-and-decisions.md) only when classifying a claim. Load [start from the outcome](../principle-start-from-the-outcome/SKILL.md) when it could change the framing or support an explicit citation.

1. Restate the request as the people affected, what they are trying to achieve, how they do it today if that is known, the intended outcome, and the proposed feature if one was supplied.
2. Keep the feature distinct from the need. State what is not part of the problem.
3. Set a discovery goal first: the decision this work must support, its uncertainty, and how you will know the framing is finished. Name the decision owner when known. Otherwise mark the owner unknown.
4. Separate the user outcome from the business/service outcome and explain their proposed connection or conflict. Record baseline/source when available; do not invent metrics. Load relevant [learning-loop](../design-product/references/learning-loop.md) sections only when synthesizing or selecting an opportunity in this turn.

Do not compare solutions, specify an interface, or treat the original feature as the requirement. A stakeholder's request is **given**, not an observed user need.

**Reply:** the problem, the people, the outcome, the proposed feature kept separate, and the discovery goal.
